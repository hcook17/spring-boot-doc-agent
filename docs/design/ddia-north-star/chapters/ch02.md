# Chapter 2. Data Models and Query Languages

## One-sentence thesis

The data model shapes what is easy to express, evolve, and query — document and relational tradeoffs are real.

## Who this chapter is for

Anyone designing schemas for target Spring apps or for this repo’s JSON/artifact models.

## What it covers

How entities and relationships are represented and queried.

## When to apply

New entity types, join-heavy features, or choosing document blobs vs normalized tables.

## Where it shows up in systems

Customer JPA/entities; this repo’s catalog.json, facts, baselines.

## Why it matters

Wrong model creates permanent accidental complexity (`maintainability-operability-evolvability`).

## How to use it here

Map access patterns first; encode relationships explicitly; evolve with schema discipline (ch05).

## Section map

- Relational Model Versus Document Model
- Many-to-One and Many-to-Many Relationships

### Relational Model Versus Document Model

- Document vs relational is a locality/join tradeoff, not a morality play.
- Fail if a document blob is treated as SoR without a schema/evolution story.

### Many-to-One and Many-to-Many Relationships

- Many-to-many needs an explicit edge; a unary map cannot represent it.
- Fail if a 1:1 map is used where the domain is many-to-many (cite fact-store / claim edges).

### Data Query Languages

- Query languages declare what to fetch; they do not invent a second SoR.
- Fail if query-layer caches become writers.

### Graph-Like Data Models

- Graph/property models fit relationship-heavy domains; still need SoR discipline.
- Fail if graph edges are hand-edited in a derived view without regenerator.

## Digested claims

- Document vs relational is about locality and join cost, not fashion.
- Many-to-many usually needs an explicit relationship representation.
- Query language choice constrains evolvability and access patterns.
- Graph models fit highly connected domains; do not force them elsewhere.
