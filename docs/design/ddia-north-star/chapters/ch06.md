# Chapter 6. Replication

## One-sentence thesis

Replication buys durability and scale at the cost of lag and conflict — lag is not optional magic.

## Who this chapter is for

Reviewers of dual homes, multi-writer docs, or “eventual” views.

## What it covers

How copies stay (or fail to stay) consistent.

## When to apply

Any second writer or async view of the same fact.

## Where it shows up in systems

STATUS vs queue; certification vs facts; mirrored docs under claude/ vs docs/design.

## Why it matters

Silent LWW of prose and code created the coverage blindspot.

## How to use it here

Prefer single writer + recompute; cite `rel-conflict-vs-recompute`; file deviations for true multi-writer.

## Section map

- Leaders and Followers
- Problems with Replication Lag
- Multi-Leader Replication

### Leaders and Followers

- Single-leader replication makes write ownership clear; lag is still real.
- Fail if a follower/read replica is treated as SoR for writes.

### Problems with Replication Lag

- Lag creates stale reads; applications must name freshness expectations.
- Fail if lag is papered over with silent last-write-wins merges.

### Multi-Leader Replication

- Multi-leader invites concurrent writes and conflict resolution policy.
- Fail if multi-writer is introduced without conflict vs recompute policy.

### Leaderless Replication

- Quorums trade availability for consistency; still need conflict policy.
- Fail if quorum reads are claimed while LWW silently drops values.

## Digested claims

- Follower lag means readers can see stale state.
- Multi-leader and leaderless designs create conflict classes you must name.
- LWW is a conflict strategy with data loss risk — not a default.
