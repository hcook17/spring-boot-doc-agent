# Chapter 5. Encoding and Evolution

## One-sentence thesis

Encodings must evolve because data outlives code; compatibility is a schema discipline under skew.

## Who this chapter is for

Anyone changing baselines, JSON schemas, Pydantic models, or fixture formats.

## What it covers

Forward/backward compatibility, schema evolution, dataflow modes.

## When to apply

Any additive or breaking change to on-disk or over-wire shapes.

## Where it shows up in systems

catalog.schema.json, semgrep FP baseline, certification shapes, check_repo_claims predicates.

## Why it matters

Inventing fake SoR numbers to satisfy a new field is a band-aid (`dev-fp-ratchet-separate-from-recall`).

## How to use it here

Additive first; version bumps with migration; separate ratchets when failure directions invert.

## Section map

- Formats for Encoding Data
- Modes of Dataflow

### Formats for Encoding Data

- Schemas (explicit or implicit) are contracts across versions of writers/readers.
- Fail if a format change breaks forward/backward compatibility without a migration plan.

### Modes of Dataflow

- DB, RPC, and async message flows each carry evolution constraints.
- Fail if additive schema needs are met by silent field renames in SoR JSON.

## Digested claims

- Data outlives code; old encodings remain until migrated.
- Compatibility: prefer additive fields with defaults under skew.
- Schemas help multi-language evolution and tooling.
- DB vs RPC vs event dataflow have different evolution constraints.
