# Chapter 1. Trade-Offs in Data Systems Architecture

## One-sentence thesis

Architecture is tradeoffs among operational vs analytical needs, SoR vs derived data, and distribution costs — not free upgrades.

## Who this chapter is for

Architects, principals, and anyone choosing homes for facts vs views in this product or a target Spring system.

## What it covers

The vocabulary for SoR vs derived, operational vs analytical, and when distribution is worth the cost.

## When to apply

Before new artifact homes, dual writers, or “just cache it” decisions; at ADR and PR design review.

## Where it shows up in systems

Pipeline facts vs certification; rules vs coverage baselines; STATUS vs code; customer DB vs read models.

## Why it matters

Without this chapter’s distinctions, teams invent second SoRs and call them caches.

## How to use it here

Name writer and readers; prefer recompute over LWW; cite `sor-vs-derived` / `rel-sor-feeds-views`; file deviations when departing.

### Operational Versus Analytical Systems

- Operational workloads need low-latency point access; analytical need scans and aggregates.
- Mixing both in one store without naming the tradeoff creates accidental complexity.
- Fail if an analytical bulk job is treated as an operational SoR writer.

### Systems of Record and Derived Data

- SoR holds each fact once; derived data is recomputable; on discrepancy SoR wins.
- One SoR can feed many views; views must not silently become writers.
- Fail if a dual writer ships without a deviation (`sor-vs-derived`, `rel-sor-feeds-views`).

### Cloud Versus Self-Hosting

- Cloud shifts ops burden; it does not erase partition, encoding, or SoR questions.
- Fail if “managed service” is used as a substitute for naming the writer of a fact.

### Distributed Versus Single-Node Systems

- Distribution buys scale/availability at the cost of partial failure and coordination.
- Fail if distribution is defaulted without a concrete scale or fault need.

### Data Systems, Law, and Society

- Legal/societal constraints (retention, confidentiality) can dominate technical elegance.
- Fail if confidentiality / retention constraints are only oral and not in SoR docs.

## Digested claims

- Operational vs analytical workloads differ in access patterns and latency expectations.
- SoR holds each fact once; derived data is recomputable; on discrepancy SoR wins by definition.
- Cloud and distribution are tradeoffs (ops burden, failure modes, cost), not default wins.
- Legal/societal constraints can dominate technical elegance — document them as first-class.
