# Chapter 3. Storage and Retrieval

## One-sentence thesis

Storage engines trade write path, read path, and compaction — indexes are derived data with a cost.

## Who this chapter is for

Engineers choosing indexes, caches, or analytical stores.

## What it covers

How on-disk structures serve queries.

## When to apply

Performance work, new indexes, analytical pipelines.

## Where it shows up in systems

Target DB indexes; this repo’s materialized views (certification, baselines).

## Why it matters

Treating an index/cache as SoR recreates dual-writer bugs.

## How to use it here

Treat indexes/views as derived; measure rebuild cost; cite `materialized-views-and-caches`.

## Section map

- Data Structures That Power Databases
- Transaction Processing or Analytics?
- Column-Oriented Storage

### Data Structures That Power Databases

- Indexes are derived structures optimizing reads; rebuildable from SoR.
- Fail if an index/baseline is hand-edited as if it were SoR.

### Transaction Processing or Analytics?

- OLTP vs OLAP access patterns differ; mixing without naming the tradeoff hurts.
- Fail if analytical scans block operational paths without a capacity plan.

### Column-Oriented Storage

- Column stores optimize analytical scans; not a free SoR replacement.
- Fail if column-oriented derived stores become dual writers.

## Digested claims

- Indexes and column stores are derived structures optimized for reads.
- OLTP vs OLAP storage choices follow access patterns from ch01.
- Compaction and write amplification are operational costs of derived indexes.
