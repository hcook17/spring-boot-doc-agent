# Chapter 12. Stream Processing

## One-sentence thesis

Streams derive continuous views with fresher latency — still derived, still need SoR discipline.

## Who this chapter is for

Authors of incremental/watch-mode pipelines and anyone choosing stream freshness over batch cost.

## What it covers

Continuous derivation vs batch; event logs as inputs; processing guarantees.

## When to apply

Choosing streaming freshness over batch cost; designing incremental doc/gate updates.

## Where it shows up in systems

Future incremental doc pipelines; target Kafka/stream apps; dual-emit `facts.jsonl` as ledger-friendly input.

## Why it matters

“Real-time” does not authorize dual writers.

## How to use it here

Compare freshness need vs batch; keep SoR clear; cite `batch-vs-stream-derived-state` and domain `09`.

## Section map

- Transmitting Event Streams
- Databases and Streams
- Processing Streams

### Transmitting Event Streams

- Append-only logs of facts enable multiple consumers and rebuildable views.
- Fail if a stream transport is treated as SoR without naming the writer of each event type.

### Databases and Streams

- Change-data-capture and dual-write patterns often create accidental second writers.
- Fail if CDC/dual-write is introduced without a deviation and clear SoR (`replication-lag-and-lww`).

### Processing Streams

- Stream processors fold events into derived state; ordering and exactly-once are hard.
- Name the delivery/ordering guarantee you actually have — do not claim exactly-once casually.
- Fail if “real-time” justifies skipping stage+load or replayability checks.

## Digested claims

- Streams are derived timelines, not automatic SoR.
- Fresher views still conflict with SoR on discrepancy.
- Exactly-once and ordering are hard; name the guarantee you actually have.
