# Constraints

One entry per real constraint this plugin operates under, tagged by kind. The point of this file is the same as `skills/document-spring-repo/references/doc-taxonomy.md`'s for the fourteen output files: a single place a new contributor (or a session picking this repo back up cold) reads first, instead of these facts being scattered across `README.md`, `SKILL.md`, commit history, and prose in old handoff docs. Written 2026-07-23 in response to `claude/steering-prompts/03-constraints-research-prompt.md`; cross-linked from `README.md` and `skills/document-spring-repo/SKILL.md`.

Five kinds of entry below. The first four are the categories `03-constraints-research-prompt.md` specified; **Enterprise-readiness gap** is a fifth added here because a 2026-07-23 competitive analysis (arXiv precedent check, GitHub comparator survey, and a direct audit of this repo) surfaced several concrete, evidence-backed gaps that don't fit cleanly under the other four but are exactly the kind of thing this file exists to make legible.

---

## Runtime prerequisites

1. **`ast-grep` binary on `PATH`** — hard dependency for the entire deterministic layer (`spring_signal_scan.py`, `spring_drift_check.py`'s tier 2). Stage 0 fails fast with an install pointer if it isn't present. `cargo install ast-grep` or `npm install -g @ast-grep/cli`.
2. **SQLLineage** (`pip install sqllineage`) — soft dependency, used only for native-query (`query_kind: "native"`) source/target table extraction. A missing install degrades that one `lineage` field per affected entry rather than failing the scan — same pattern as the next item.
3. **`pathspec`** (`pip install pathspec`) — soft dependency, used only when the opt-in `--respect-gitignore` flag is passed to `spring_signal_scan.py` or `partition_repo.py`. Missing install silently disables the flag's Python-side matching (`load_gitignore_spec` returns `None` on `ImportError`); default behavior (flag omitted) is unaffected either way.
4. **None of the above are version-pinned anywhere in the repo.** No `requirements.txt` or `pyproject.toml` exists (confirmed absent). A future `ast-grep` release with a breaking CLI-flag or output-shape change, or a `sqllineage`/`pathspec` release with a breaking API change, would surface as a silent behavior change rather than a version-mismatch error at install time.

## Integration gaps, not scope cuts

1. **`spring_drift_check.py`** is a real, tested (12/12 passing) two-tier drift detector — now documented as an optional Stage 0 pre-flight check in `SKILL.md` and in `README.md`'s "On drift detection" section — but it is still standalone: not invoked automatically by the `document-spring-repo` pipeline, and not triggered by CI (there is no CI at all — see next item). You run it by hand, when you happen to have a prior `spring_signals.json` and decide to check it.
2. **No CI/CD wiring anywhere in this repo.** Confirmed absent: no `.github/workflows/`, no `.gitlab-ci.yml`, no equivalent. All three test suites (`test_spring_signal_scan.py`, `test_partition_repo.py`, `test_spring_drift_check.py`) are run by hand only — nothing prevents a commit that breaks one of them from landing.
3. **No run-level telemetry or manifest.** `claude/steering-prompts/04-analytics-logging-research-prompt.md` proposes a `run_manifest.json` (timestamp, target repo + commit hash, per-stage timing/pass-fail, evidence-tag counts, interview answered/skipped breakdown); it isn't built yet. Today there is no way to know, short of reading all fourteen generated files by hand, how many claims landed `Unknown` vs. `Evidenced` vs. `Confirmed`, or whether the interview stage was skipped for a given run.

## Known precision tradeoffs

1. **Source-text (ast-grep/tree-sitter) analysis vs. compiled-bytecode/ArchUnit analysis.** Trades some precision (won't resolve inherited annotations, annotations picked up only via meta-annotations, interfaces implemented indirectly) for not needing a build step or classpath. Already documented in `README.md`; recorded here for cross-linking.
2. **JPQL queries never get SQL-lineage extraction.** `@Query` values tagged `"query_kind": "jpql"` reference entity names, not table names, and aren't valid SQL grammar at all — a known, fundamental limitation of general-purpose SQL lineage tooling generally (SQLLineage included), not something specific to this scanner. Native queries do get lineage extraction (see Runtime prerequisites above).
3. **Cross-group relationship detection (the `references` bucket / import-package index) has real, stated limits**, per `IMPLEMENTATION_HANDOFF.md` item 6: same-package files split across different partition groups with no import statement between them aren't caught (DFS locality only rescues same-group or adjacent-group cases); wildcard imports (`import com.foo.*`) resolve to a package, not a specific class; interface-mediated dependency injection (`@Autowired` on an interface type) isn't recoverable from an import graph alone. This closes the specific controller-calls-service gap that motivated it — it is not a complete call graph.
4. **No published precedent for `spring_drift_check.py`'s specific drift-detection design** (tier-1 whole-repo file-hash, tier-2 targeted per-citation ast-grep re-verification) was found in a 2026-07-23 arXiv search. The closest published work (arXiv:2506.16440, "Evaluating LLMs for Documentation-to-Code Traceability," Jun 2025) uses LLM-based trace-link inference instead, and reports that while trace-link *identification* reaches ~79–80% F1, full-explanation *correctness* is only 43–71% — the authors recommend human-in-the-loop verification. `spring_drift_check.py` avoiding an LLM judgment call entirely (re-deriving the same deterministic identity `spring_signal_scan.py` itself extracts, per rule type) is a deliberate departure from that literature, not an oversight — but it means this design has no direct academic precedent to point to, only this indirect argument for why the departure is justified.

## Confidentiality/handling rules

1. **Standing rule** (promoted here from one-time handoff prose per `claude/steering-prompts/03-constraints-research-prompt.md`, which named it "the real-repo-name/content rule" but whose exact original wording isn't reachable from this repo — this is a fresh statement of the same intent, not a verbatim carry-forward, and should be treated as a first draft to reconcile against the original if that text ever resurfaces): **when this plugin is run against a real target repository, that repository's actual name and any excerpt of its actual source, config, or generated docs must not be pasted into this plugin's own tracked files** (commit messages, `claude/session-log.md`, steering-prompt research, issues) beyond what's needed to describe a bug mechanically (e.g., "a `vendor/` directory containing Java" is fine; a real client's package names or entity names are not). Use synthetic or already-public example names instead, the same way this repo's own `scripts/test_fixtures/spring_signals/` fixture tree does.
2. **Secret/credential leakage into generated docs — a real, currently unmitigated gap**, found during a 2026-07-23 audit. The deterministic layer itself is clean: `spring_signal_scan.py` extracts configuration/deployment evidence by filename and annotation-site matching only (`@ConfigurationProperties`, `@Value`, the presence of `application.yml`/`Dockerfile`) and never reads config *values*, so nothing in `spring_signals.json` can carry a leaked secret forward. But Stage 1 `file-summarizer` subagents read full file content directly, including `application.yml`/`.properties` files that, in real Spring Boot repos, commonly carry hardcoded secrets in local/dev profiles — and nothing in `agents/*.md` or `doc-taxonomy.md` instructs a subagent to redact a real secret value it encounters. The existing guidance (`doc-taxonomy.md`'s configuration.md notes) only says not to *fabricate* example secret values; it says nothing about not *echoing a real one*. This is open, not yet mitigated — worth closing before running this pipeline against any repo where dev-profile secrets are plausible.

## Enterprise-readiness gaps

Findings from a direct, evidence-based audit of this repo's own posture (2026-07-23), for anyone evaluating this plugin for use beyond a single operator's own machine.

1. **License**: `.claude-plugin/plugin.json`'s `license` field is `"UNLICENSED"`. Blocks any procurement/legal approval for use beyond the author's own machine outright — this is the single highest-priority item on this list to close before any wider rollout.
2. **No RBAC or auth layer of any kind.** The plugin is gated entirely by whatever filesystem and LLM access the operator's own Claude Code session already has — there is no separate concept of "who is allowed to run this" (confirmed by absence: no auth/permission code anywhere outside the unrelated `@PreAuthorize` extraction rule and the `authorization.md` output file, both about the *target repo's* security, not this plugin's own).
3. **No audit trail of pipeline runs** — see "no run-level telemetry" above.
4. **No multi-repo or batch story.** Every invocation takes exactly one `<repo_path>` argument; there's no mechanism to run this against, or aggregate results across, multiple services at once — a common enterprise ask ("document all N of our Spring services") this plugin doesn't address today.
5. **Dependencies unpinned** — see Runtime prerequisites above.

**If bringing this into an actual enterprise rollout, close in roughly this order**: license → confidentiality/secret-redaction → CI wiring for `spring_drift_check.py` and the existing test suites → dependency pinning → audit trail / run manifest → RBAC / multi-repo support (lowest urgency of this list, and the furthest from what a single-operator tool needs first).
