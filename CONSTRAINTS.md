# Constraints

One entry per real constraint this plugin operates under, tagged by kind. The point of this file is the same as `skills/document-spring-repo/references/doc-taxonomy.md`'s for the fourteen output files: a single place a new contributor (or a session picking this repo back up cold) reads first, instead of these facts being scattered across `README.md`, `SKILL.md`, commit history, and prose in old handoff docs. Written 2026-07-23 in response to `claude/steering-prompts/03-constraints-research-prompt.md`; cross-linked from `README.md` and `skills/document-spring-repo/SKILL.md`.

Five kinds of entry below. The first four are the categories `03-constraints-research-prompt.md` specified; **Enterprise-readiness gap** is a fifth added here because a 2026-07-23 competitive analysis (arXiv precedent check, GitHub comparator survey, and a direct audit of this repo) surfaced several concrete, evidence-backed gaps that don't fit cleanly under the other four but are exactly the kind of thing this file exists to make legible.

## Runtime prerequisites

1. **`ast-grep` binary on `PATH`** — hard dependency for the entire deterministic layer (`spring_signal_scan.py`, `spring_drift_check.py`'s tier 2). Stage 0 fails fast with an install pointer if it isn't present. `cargo install ast-grep` or `npm install -g @ast-grep/cli`. **Confirmed empirically, 2026-07-24**: a fresh environment without it on `PATH` fails `test_capacity_preflight.py` outright (that suite imports `spring_signal_scan`, which shells out to `ast-grep`), not just Stage 0 itself.

   **[Partially resolved, 2026-07-24 — corrected from `[Resolved]` on 2026-07-24]** The entry below was written ahead of its own evidence: it was true of `find_ast_grep()`, the function it examined, and generalized to the file. It was not true of `run_ast_grep()` in the same module, which kept two `sys.exit(1)` calls covering the *other* ast-grep failure mode — binary present but failing, via a malformed rule file, a bad `--globs` argument, or output that will not parse as JSON. Since `scan()` calls `run_ast_grep()` and three suites call `scan()` from `setUpClass`, that path reproduced the identical silent-process-death this entry describes as fixed. **Now genuinely closed**: an `AstGrepError(RuntimeError)` base class was added, `AstGrepNotFoundError` subclasses it (so every existing `except AstGrepNotFoundError` keeps its exact prior meaning), `run_ast_grep()` raises rather than exits, and the three CLI entry points catch the base class — same stderr text, same exit code 1. Six tests in `test_spring_signal_scan.py` pin it, four of them asserting the property that actually matters: that a plain `except Exception` catches the failure. Verified non-vacuous by reverting both call sites and confirming 5 of the 51 tests error with `SystemExit: 1`. The drift direction here is worth naming: the claim was not falsified by later code, it was **over-stated when written** — a `[Resolved]` covering one function presented as covering a file.

   Original entry, corrected above but kept because its reasoning is still the reason the fix looks the way it does:

   **[Resolved, 2026-07-25]** `find_ast_grep()` (`scripts/spring_signal_scan.py`) used to call `sys.exit(1)` directly when the binary was missing. FAILED (errors=4)`, a normal summary line, instead of the process dying silently). The three CLI entry points that call it (`spring_signal_scan.py main()`, `spring_drift_check.py main()`, `capacity_preflight.py main()`) each catch `AstGrepNotFoundError` explicitly and print the same friendly stderr message + `sys.exit(1)` as before — confirmed the CLI's user-facing behavior is unchanged (`error: the 'ast-grep' binary is not on PATH...`, exit code 1, no raw traceback). ## Known precision tradeoffs

1. **Source-text (ast-grep/tree-sitter) analysis vs. compiled-bytecode/ArchUnit analysis.** Trades some precision (won't resolve inherited annotations, annotations picked up only via meta-annotations, interfaces implemented indirectly) for not needing a build step or classpath. Already documented in `README.md`; recorded here for cross-linking.
2. **[Resolved for the bounded common case, 2026-07-25] JPQL queries now get SQL-lineage extraction for the single-entity, no-join case.** Previously framed here as a fundamental limitation; research (arXiv, GitHub, DeepWiki — see `claude/session-log.md`'s 2026-07-25 entry) found no published technique or usable open-source tool for JPQL/HQL-to-SQL lineage translation exists (confirmed by an open, unresolved `reata/sqllineage#461` issue asking for exactly this), but also that this scanner already builds the one piece such a translation actually needs: `entity_table_map` (class name -> table name, from `@Entity`/`@Table` scanning). `resolve_jpql_to_lineage()` (`scripts/spring_signal_scan.py`) now resolves `FROM <Entity> <alias>` JPQL to real table lineage by looking up the entity, stripping the alias prefix, and feeding the rewritten pseudo-SQL through the same `extract_sql_lineage()` native queries use — validated as directionally consistent with how Hibernate's own SQM pipeline resolves JPQL (metamodel-driven name lookup), just at a much smaller scope.

   **Explicitly, permanently out of scope** (each would need more than a rewrite to resolve correctly, so degrading to `{"available": false, ...}` is the honest answer, not a placeholder for "not yet built"): multi-entity `FROM` (joins, comma-separated entities); association-traversal paths through the alias (`u.orders.total`); JPQL-only relationship functions (`SIZE`, `KEY`, `VALUE`, `INDEX`, `TYPE`); `@Entity(name=...)` overrides (`entity_table_map` is keyed by Java class name only, so an override query correctly reports "not found" rather than a wrong resolution); polymorphic `FROM` (naming a superclass/interface — inherently multi-table under JOINED/TABLE_PER_CLASS inheritance); embedded/composite keys (`@EmbeddedId`/`@IdClass` paths like `i.id.customerId`, which need embeddable-aware resolution a flat class-name map doesn't provide). See `resolve_jpql_to_lineage()`'s own docstring for the authoritative, most up-to-date version of this list.

   **[New info — the "rather than a wrong resolution" claim above has one exception, 2026-07-24]** Keying on the simple class name means two `@Entity` classes in different packages *collide*, and that case does produce a wrong resolution rather than a "not found": the map holds one entry, so a JPQL query in the losing class's package resolves to the winner's table. Until 2026-07-24 the winner was whichever match `ast-grep` emitted last — unstable across runs on identical input, so the same repo could resolve the same query to different tables on consecutive scans. `spring_signal_scan.py` now resolves collisions on lowest file path, which makes the outcome deterministic and re-verifiable but **not** correct — it is an arbitrary winner, chosen for stability. Detecting the collision and emitting `contested` (per `claude/10-architecture-maturation-plan.md:154`) is the real fix and is not built.

   **[Resolved, 2026-07-25] This introduced a real drift-check blind spot, now closed.** A JPQL citation's lineage is *derived* from two files, not one — the query text (its own file) and the entity's table mapping (`entity_table_map[entity]["file"]`, typically a different file). `spring_drift_check.py`'s per-file tier-1/tier-2 model implicitly assumed every citation's freshness depends on exactly its own file, so a table rename in the entity's file alone (query file untouched) would have gone completely undetected — the JPQL citation would report `unchanged` while its lineage was actually stale. Fixed by generalizing the existing freshness rule instead of special-casing JPQL: `resolve_jpql_to_lineage()` now stamps `lineage.resolved_via_entity`, and a new post-loop pass (`_reverify_jpql_lineage_provenance()`, `scripts/spring_drift_check.py`) re-derives a JPQL citation's freshness from *all* of its provenance files, reusing `_recheck_entities()`'s already-computed fresh entity data (zero extra `ast-grep` invocations) and reusing the existing `STATUS_CONFIRMED`/`STATUS_DRIFTED` vocabulary rather than adding a new status. See that script's module docstring ("DERIVED CITATIONS HAVE MORE THAN ONE INPUT") for the full design.

   **[New info — the wording above ran ahead of the code, corrected 2026-07-24]** "*All* of its provenance files" was the design's intent but not yet its behavior when this entry was written. As first merged, the pass re-derived freshness only for the subset where the entity's file was **modified** and the query's own file was untouched; two gates missed the rest. First, it skipped any citation whose own-file verdict wasn't `STATUS_UNCHANGED` — so a query file that changed *without* its query text changing earned `confirmed_still_present` from `_recheck_queries()` (which verifies text presence, and says nothing about lineage) and then never had its entity provenance checked at all, reporting stale lineage as confirmed. Second, the gate tested `changed_set` alone, so **deleting or moving** the entity's file left dependent JPQL citations sitting at `unchanged`. PR #30 (`a677279`) closed both — widening the gate to `changed_set ∪ deleted_set` and narrowing the skip to an already-`DRIFTED` own-file verdict, each with a regression test that fails without the fix. The claim above is accurate as of that commit, not as of the one that first made it. Worth keeping as a worked example of the failure mode `CLAUDE.md`'s CONSTRAINTS check now exists to catch: a `[Resolved]` tag that describes the intended end state rather than the code as merged reads as settled, and nothing mechanical would have caught the gap.
3. **Cross-group relationship detection (the `references` bucket / import-package index) has real, stated limits**, per `IMPLEMENTATION_HANDOFF.md` item 6: same-package files split across different partition groups with no import statement between them aren't caught (DFS locality only rescues same-group or adjacent-group cases); wildcard imports (`import com.foo.*`) resolve to a package, not a specific class; interface-mediated dependency injection (`@Autowired` on an interface type) isn't recoverable from an import graph alone. This closes the specific controller-calls-service gap that motivated it — it is not a complete call graph.

   **[Partially resolved, 2026-07-24]** The first limb no longer holds. `scripts/build_cross_group_edges.py` (commit `abd3ade`) resolves the package/import join once in Stage 0 and emits same-package-split-across-groups explicitly as `same_package_outside` adjacency, so it is now caught rather than relying on DFS locality — and on the first real repo measured it was the *largest* class of cross-group relationship (1,222 adjacency rows against 1,995 cut arcs). The other two limbs stand, but are now *recorded* rather than silent: a wildcard import resolves with `confidence: "package-fanout"` and an unresolvable one as `"unresolved"`, so a reader can see which relationships are approximate instead of inferring their absence.
4. **No published precedent for `spring_drift_check.py`'s specific drift-detection design** (tier-1 whole-repo file-hash, tier-2 targeted per-citation ast-grep re-verification) was found in a 2026-07-23 arXiv search. The closest published work (arXiv:2506.16440, "Evaluating LLMs for Documentation-to-Code Traceability," Jun 2025) uses LLM-based trace-link inference instead, and reports that while trace-link *identification* reaches ~79–80% F1, full-explanation *correctness* is only 43–71% — the authors recommend human-in-the-loop verification. `spring_drift_check.py` avoiding an LLM judgment call entirely (re-deriving the same deterministic identity `spring_signal_scan.py` itself extracts, per rule type) is a deliberate departure from that literature, not an oversight — but it means this design has no direct academic precedent to point to, only this indirect argument for why the departure is justified.
5. **[New info — 2026-07-24] Byte-determinism of the scan output is now an asserted invariant, not an assumed one.** This file's framing elsewhere treats byte-stable output as a property the deterministic layer obviously has. It did not have it. `entity_table_map` was populated in `ast-grep`'s multithreaded match order and emitted unsorted, so identical scans of an unchanged repo serialized to different bytes — measured on the fixture as `['LegacyAudit', 'Invoice', 'SLARule', 'PaymentLedger']`. Every downstream consumer hashes raw bytes, so no assertion of the form "this artifact is unchanged" was reliable. Now sorted on emit, pinned by tests, and verified byte-identical across three separate processes against a real 615-file Spring service.

   Recorded because it generalizes past this one bug: the naive probe — run the scan twice, diff the bytes — **passed against the unfixed scanner**, because two calls inside one process observed the same match order. Only the explicit `keys == sorted(keys)` assertion caught it. Re-run-and-diff detects only nondeterminism that varies under the conditions it happens to vary; name the invariant where one exists. This is the argument for preferring an invariant over a probe, and it is also why reproducibility tooling earns its keep by *varying the environment* rather than by re-running.

6. **[Flagged, not yet resolved — 2026-07-24] Overlap can cascade past adjacent groups when groups are small.** `partition_repo.py`'s design is ~10% overlap between *adjacent* groups, and `test_partition_repo_real_world.py` already asserts no file is counted more than twice. Both are violated when a group is small enough that its own ~10% tail consists of files that were themselves carried *into* it: the carry propagates again and a file lands in three consecutive groups, so Stage 1 summarizes it three times. Reproduced deterministically at `--max-tokens 2000` and `3000`; it does not reproduce at `1000` or `4000`, and never at the `120000` default — which is exactly why no existing suite catches it. Pinned as an `expectedFailure` in `scripts/test_enterprise_kitchen_sink.py` (`Ch06PartitioningTest`), so a fix reports as an unexpected success rather than passing silently. The real fix is for `carry_forward()` to exclude files that were themselves carried in; not built.

7. **[Flagged, not yet resolved — 2026-07-24] Multi-segment Spring profile names are not recognized as configuration at all.** `spring_signal_scan.py`'s `CONFIG_NAME_PATTERNS` matches `^application(-[\w.]+)?\.(ya?ml|properties)$`, and `[\w.]+` excludes the hyphen. So `application-prod.yml` is scanned while `application-dev-local.yml` — an entirely ordinary profile name — is not: no `config_key_sets` entry, no `redaction_zones`, and therefore **no credential scanning of a file that plausibly holds credentials**. That last consequence is why this sits next to the confidentiality entries below and not only here. A one-character widening (`[\w.-]+`) closes it, deliberately not applied here because it changes which files the scanner ingests. Pinned in `Ch04EncodingTest`.

8. **[Flagged, not yet resolved — 2026-07-24] A write into a gitignored path is invisible to the write-scope gate.** `check_pipeline_output.py`'s "no writer went outside `docs/`" check is built on `git status --porcelain`, which never reports ignored paths. A doc-writer that wrote into `target/`, `build/`, or any other gitignored directory therefore passes the gate silently. This is the structural control that `SKILL.md` describes as needing "no cooperation from the agent," so the hole matters more than its likelihood suggests. Pinned in `Ch12GateResponsibilityTest`.

9. **[Flagged, not yet resolved — 2026-07-25] Tier 2's generic comparison reads the first LINE of a match, so wrapping an annotation across lines reports drift that did not happen.** Item 4 above notes this design has no published precedent to compare against; this is the first measurement of its precision, so it is a number rather than an argument. `spring_signal_scan._first_line_match()` supplies the citation identity for the 20 of 23 rules with no specialized extractor (`persistence__entity`, `persistence__repository` and `raw_queries__query` are the three exceptions, and re-derive structured identities instead). ast-grep returns the whole match; that function keeps `text.splitlines()[0]`, so `@RequestMapping(\n    "/api/invoices"\n)` reduces to `@RequestMapping(` and matches nothing. **Measured across four formatting-only perturbations of `scripts/test_fixtures/spring_signals/`: 2 false positives in 208 citation checks, all in `api_surface__mapping`.** Comments, reindentation and inserted blank lines each produce zero — this is one specific class, not general brittleness. Two candidate identities reach 0/208 with no loss of real-change detection (`drift_match_normalizers.py`); for the current table run `python3 scripts/test_drift_normalization.py`, which re-derives every row rather than trusting one written here. **Deliberately not fixed in the same change as the measurement**: `_first_line_match()` decides both what tier 2 *compares* and what `spring_signals.json` *stores* in each citation's `match` field, which is human-readable evidence a doc-writer agent consumes. Separating those two jobs changes the stored schema, so it is its own decision with its own blast radius. The fixtures already contain one instance of the defect in committed data — `InvoiceController.java`'s multi-line `@PreAuthorize` is stored as the truncated `@PreAuthorize(`.

## Confidentiality/handling rules

1. **Standing rule** (promoted here from one-time handoff prose per `claude/steering-prompts/03-constraints-research-prompt.md`, which named it "the real-repo-name/content rule" but whose exact original wording isn't reachable from this repo — this is a fresh statement of the same intent, not a verbatim carry-forward, and should be treated as a first draft to reconcile against the original if that text ever resurfaces): **when this plugin is run against a real target repository, that repository's actual name and any excerpt of its actual source, config, or generated docs must not be pasted into this plugin's own tracked files** (commit messages, `claude/session-log.md`, steering-prompt research, issues) beyond what's needed to describe a bug mechanically (e.g., "a `vendor/` directory containing Java" is fine; a real client's package names or entity names are not). Use synthetic or already-public example names instead, the same way this repo's own `scripts/test_fixtures/spring_signals/` fixture tree does.

   **[Violated and fixed, 2026-07-25 — the rule needed widening, not just obeying]** This rule was broken by the very mechanism written to enforce it. `.gitignore` carried `/<real service name>/` so that a stray `git add -A` could not publish a ~101MB third-party checkout — but `.gitignore` is itself tracked, and this repo is public, so the ignore rule published the one thing it existed to protect: the directory name alone identifies the client service. The list above ("commit messages, `claude/session-log.md`, steering-prompt research, issues") enumerates *prose* carriers and simply did not imagine a config file leaking a name. **Read it as covering every tracked file, including ones nobody thinks of as documentation** — `.gitignore`, workflow YAML, fixture paths, `Makefile` targets. Fixed by moving the machine-specific name into `.git/info/exclude` (per-clone, never pushed) and leaving only generic patterns plus a pointer in `.gitignore`; the exposure never reached `main`. Caught by the repo owner on review, not by any check — nothing mechanical looks for this, which is worth knowing before treating the rule as self-enforcing.
2. **[Resolved, heuristically — not a guarantee] Secret/credential leakage into generated docs**, found during a 2026-07-23 audit. The deterministic layer stays exactly as clean as before: `spring_signal_scan.py` still never reads config *values* into its own output — but it now also runs a heuristic pass (`scripts/_secret_heuristics.py`: secret-shaped key names with a non-placeholder literal value, plus key-agnostic patterns for AWS access key IDs and PEM private-key blocks) over configuration/deployment files and records `redaction_zones` (file + line + which heuristic fired, never the matched value) in `spring_signals.json`. `agents/file-summarizer.md` and `agents/doc-writer.md` are both instructed to never transcribe a flagged line's literal value, and `doc-taxonomy.md`'s configuration.md notes now say so explicitly (previously only warned against *fabricating* example secrets, said nothing about echoing a real one). Defense in depth, not just a prompt instruction: `scripts/check_no_secrets_leaked.py` re-applies the same heuristics to a completed run's own output (`summaries.json`, `docs/*.md`) and flags anything that made it through anyway — documented in `SKILL.md` as an optional post-run check, not CI-wired (no target-repo output exists in this repo's own CI to check). Stated residual scope: heuristic, not exhaustive — a secret under an unrecognized key name, embedded in free-text prose rather than a reproduced `key: value` line, isn't caught unless it also matches one of the two key-agnostic patterns. See `_secret_heuristics.py`'s own docstring for the exact boundary.

   **[New info — the stated scope held in principle but not on line 1, fixed 2026-07-24]** This entry claimed the heuristic pass runs over configuration/deployment files, and it did — except on the first line of any BOM-prefixed file. `spring_signal_scan.py` read config with `encoding="utf-8"` rather than `utf-8-sig`, so a BOM survived as a literal `﻿`, which is Unicode category `Cf` and therefore matches neither `\s` nor `\w`. Every `^\s*`-anchored regex downstream (`_config_keys.py`'s `_YAML_KEY_LINE_RE`, `_secret_heuristics.py`'s `KEY_VALUE_LINE_RE`) failed on that line: a credential sitting on line 1 of a BOM'd `application.yml` was never flagged, and when line 1 was a group header it never entered the indent stack, so every descendant key silently lost its prefix (`spring.datasource.url` became `datasource.url`). Now reads `utf-8-sig`; regression-tested against byte-identical BOM/no-BOM twins in `scripts/test_enterprise_kitchen_sink.py` (`Ch04EncodingTest`). Noted rather than silently corrected because the failure was invisible from the output — the key set looked plausible and was wrong.

**A second, complementary signal for repos where config files are checked-in placeholders, not real secrets** (real values injected by an external service at deploy time — value-content heuristics matter less there, since nothing sensitive is actually committed): `spring_signal_scan.py` also records each config/deployment file's dotted key *set* (`config_key_sets`, names only, schema_version >= 5, `_config_keys.py`), and `spring_drift_check.py` uses it to tell apart two very different reasons a config file's content might change between scans — a key added/removed (`config_structure_changed`, an expected, structural evolution) versus the exact same keys with different values (`config_values_only_changed_review_needed`, worth a human look since nothing should be editing a value in-repo if the key structure didn't need to change too). See `spring_drift_check.py`'s "WHAT HAPPENS TO CITATIONS WITH NO rule_id" docstring section for the full design.

## Enterprise-readiness gaps

Findings from a direct, evidence-based audit of this repo's own posture (2026-07-23), for anyone evaluating this plugin for use beyond a single operator's own machine.

1. **[Resolved] License**: `.claude-plugin/plugin.json`'s `license` field now reads `"MIT"` — confirmed directly against the live file on 2026-07-23 (this entry previously said `"UNLICENSED"`, which was stale by the time of that audit; caught and corrected as part of the `MATURITY_ASSESSMENT.md` addition, not a new change to the field itself).
2. **No RBAC or auth layer of any kind.** The plugin is gated entirely by whatever filesystem and LLM access the operator's own Claude Code session already has — there is no separate concept of "who is allowed to run this" (confirmed by absence: no auth/permission code anywhere outside the unrelated `@PreAuthorize` extraction rule and the `authorization.md` output file, both about the *target repo's* security, not this plugin's own).
3. **No audit trail of pipeline runs** — see "no run-level telemetry" above.
4. **No multi-repo or batch story.** Every invocation takes exactly one `<repo_path>` argument; there's no mechanism to run this against, or aggregate results across, multiple services at once — a common enterprise ask ("document all N of our Spring services") this plugin doesn't address today.
5. **[Resolved] Dependencies pinned** — see Runtime prerequisites item 4 above.
6. **[Partially resolved] PRs land with zero required status checks, zero required reviews, and no issue/label linkage.** A required check now *exists* (`.github/workflows/ci.yml`, closing "Integration gaps" item 2 above) — but nothing requires it to pass before merge, and reviews are still not required. Confirmed directly on PR #9's GitHub page (2026-07-23 review): `Checks: 0`, `Reviewers: No reviews`, `1 participant`, `Successfully merging this pull request may close these issues: None yet` — and it still rendered "Ready to merge," meaning that status reflects only the absence of merge conflicts, not correctness or review. `gh api repos/<owner>/<repo>/branches/main/protection` returning 404 would confirm no branch-protection rule is configured at all; not yet checked. Deliberately left open, not overlooked: enabling branch protection is a repo-admin action with real blast radius (a misconfigured rule can lock the repo owner out of their own pushes) and out of scope for a code-only PR. The concrete next action, once the CI workflow above has gone green at least once: `gh api repos/<owner>/<repo>/branches/main/protection -X PUT -f required_status_checks[strict]=true -f 'required_status_checks[contexts][]=test' -f enforce_admins=true -f 'required_pull_request_reviews[required_approving_review_count]=1' -f restrictions=null`, run by a repo admin. This isn't specific to PR #9 — every PR in this repo's history (`claude/llms/`) has the same shape (single-author, self-merged). For a single-operator tool this is normal; for anything beyond that, this is the same underlying "no RBAC / no audit trail" gap above, now observed concretely rather than stated abstractly.

   **Current-context note, added 2026-07-25 so this reads honestly rather than as a flat deficiency:** there are no other contributors today — every merge so far has been the repo owner working with a Claude Code session. In that context, `CONTRIBUTING.md`'s write-then-verify rule (every claim hand-verified against the real commit before being written down, per `claude/llms/pr-*.md`'s own discipline) is the effective substitute for a second reviewer, not an absence of scrutiny. This doesn't make the gap disappear — the moment this becomes a team project, an unreviewed/unrequired-check merge path is a real risk again, and the `gh api` command above is still the concrete fix when that day comes — it just means "zero required reviews" shouldn't be read as "zero review happening" for this repo as it stands today.

   **Future-team workflow, sketched by the repo owner 2026-07-25, not yet built:** the intended shape once this stops being a solo project is `PR created → team reviews → team adds claude/llms/pr-N.md → QA reviews and signs off on it`. This repurposes `pr-N.md` from an author's own self-verification artifact into part of the review pipeline itself — a reviewer (not necessarily the author) writes and hand-verifies the deterministic commands as their review, and QA's sign-off is against that artifact specifically, not a bare GitHub "approve" click. Complements, doesn't replace, the branch-protection `gh api` command above: that gate enforces *that* a check/review happened; this workflow is about *what the review actually consists of*. Not yet implemented — no tooling change follows from this today, since it only matters once there's a team to run it. Revisit alongside branch protection when that day comes.

**If bringing this into an actual enterprise rollout, close in roughly this order**: ~~license~~ (done — confirmed `MIT` in `.claude-plugin/plugin.json`) → confidentiality/secret-redaction → ~~CI wiring for the existing test suites and `claude/llms/`'s own verification commands~~ (done — `.github/workflows/ci.yml`) → branch protection + required reviews → ~~dependency pinning~~ (done — `requirements.txt`) → audit trail / run manifest → RBAC / multi-repo support (lowest urgency of this list, and the furthest from what a single-operator tool needs first). See `MATURITY_ASSESSMENT.md` for the full scorecard and adoption gate checklist this list now feeds into.
