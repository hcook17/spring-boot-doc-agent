# Constraints

One entry per real constraint this plugin operates under, tagged by kind. The point of this file is the same as `skills/document-spring-repo/references/doc-taxonomy.md`'s for the fourteen output files: a single place a new contributor (or a session picking this repo back up cold) reads first, instead of these facts being scattered across `README.md`, `SKILL.md`, commit history, and prose in old handoff docs. Written 2026-07-23 in response to `claude/steering-prompts/03-constraints-research-prompt.md`; cross-linked from `README.md` and `skills/document-spring-repo/SKILL.md`.

Five kinds of entry below. The first four are the categories `03-constraints-research-prompt.md` specified; **Enterprise-readiness gap** is a fifth added here because a 2026-07-23 competitive analysis (arXiv precedent check, GitHub comparator survey, and a direct audit of this repo) surfaced several concrete, evidence-backed gaps that don't fit cleanly under the other four but are exactly the kind of thing this file exists to make legible.

## Runtime prerequisites

1. **CodeQL CLI binary on `PATH`** — hard dependency for the entire deterministic layer (`spring_signal_scan.py`, `spring_drift_check.py`'s tier 2). Stage 0 fails fast with an install pointer if it isn't present. Install the CodeQL CLI from https://github.com/github/codeql-cli-binaries/releases and add it to `PATH`. **Confirmed empirically, 2026-07-27**: a fresh environment without it on `PATH` fails `test_capacity_preflight.py` outright (that suite imports `spring_signal_scan`, which calls the CodeQL runner), not just Stage 0 itself.

   **[Resolved, 2026-07-27]** `find_codeql()` (`src/doc_engine/scanning/support/_codeql_runner.py`) and the database creation/query paths raise `CodeQLError` (a `RuntimeError` subclass) on failure. `spring_signal_scan.py` wraps these as `CodeQLScannerError`. A missing CodeQL binary no longer kills the test process with `SystemExit`; `unittest` catches the ordinary exception and reports a normal `Ran N tests ... FAILED (errors=N)` summary. The three CLI entry points (`spring_signal_scan.py main()`, `spring_drift_check.py main()`, `capacity_preflight.py main()`) catch `CodeQLScannerError` and print the same friendly stderr message + `sys.exit(1)` as before — confirmed the CLI's user-facing behavior is unchanged (`error: the 'codeql' binary is not on PATH...`, exit code 1, no raw traceback). The property that matters is that a plain `except Exception` catches the failure, which is now true for all CodeQL failure paths. Drift direction here: the dependency changed from `ast-grep` to CodeQL, but the same failure-handling invariant is preserved.
2. **SQLLineage** (`pip install sqllineage`) — **[Correction, 2026-07-24]** this was previously described here as a soft dependency that only degrades the `lineage` field on a missing install. That's true for the *scan's own runtime behavior*, but it understated the test-suite impact: a fresh environment without `sqllineage` installed failed 7/32 tests in `test_spring_signal_scan.py` (tests asserting real lineage-extraction output, which naturally can't pass if the library producing that output isn't there) — not a silent degrade, an actual test failure. Installing it (`pip install sqllineage`) brought that suite to a clean 32/32.
3. **`pathspec`** (`pip install pathspec`) — soft dependency, used only when the opt-in `--respect-gitignore` flag is passed to `spring_signal_scan.py` or `partition_repo.py`. Missing install silently disables the flag's Python-side matching (`load_gitignore_spec` returns `None` on `ImportError`); default behavior (flag omitted) is unaffected either way. Not implicated in the 2026-07-24 finding above — the failing tests were specifically lineage-related, not gitignore-related.
4. **[Resolved, 2026-07-25]** The Python runtime prerequisites are now version-pinned in a `requirements.txt` at the plugin root (`ast-grep-cli~=0.45.0`, `sqllineage~=1.5.8`, `pathspec~=1.1.1`, `semgrep~=1.171.0`), using compatible-release specifiers rather than exact pins so a fresh environment reliably gets a working version without being frozen forever. `.github/workflows/ci.yml`'s "Install Python dependencies" step now runs `pip install -r requirements.txt` instead of the previous unpinned `pip install ast-grep-cli sqllineage pathspec`. ## Known precision tradeoffs

1. **Source-text (ast-grep/tree-sitter) analysis vs. compiled-bytecode/ArchUnit analysis.** Trades some precision (won't resolve inherited annotations, annotations picked up only via meta-annotations, interfaces implemented indirectly) for not needing a build step or classpath. Already documented in `README.md`; recorded here for cross-linking.
2. **[Resolved for the bounded common case, 2026-07-25] JPQL queries now get SQL-lineage extraction for the single-entity, no-join case.** Previously framed here as a fundamental limitation; research (arXiv, GitHub, DeepWiki — see `claude/session-log.md`'s 2026-07-25 entry) found no published technique or usable open-source tool for JPQL/HQL-to-SQL lineage translation exists (confirmed by an open, unresolved `reata/sqllineage#461` issue asking for exactly this), but also that this scanner already builds the one piece such a translation actually needs: `entity_table_map` (class name -> table name, from `@Entity`/`@Table` scanning). `resolve_jpql_to_lineage()` (`src/doc_engine/tools/spring_signal_scan.py`) now resolves `FROM <Entity> <alias>` JPQL to real table lineage by looking up the entity, stripping the alias prefix, and feeding the rewritten pseudo-SQL through the same `extract_sql_lineage()` native queries use — validated as directionally consistent with how Hibernate's own SQM pipeline resolves JPQL (metamodel-driven name lookup), just at a much smaller scope.

   **Explicitly, permanently out of scope** (each would need more than a rewrite to resolve correctly, so degrading to `{"available": false, ...}` is the honest answer, not a placeholder for "not yet built"): multi-entity `FROM` (joins, comma-separated entities); association-traversal paths through the alias (`u.orders.total`); JPQL-only relationship functions (`SIZE`, `KEY`, `VALUE`, `INDEX`, `TYPE`); `@Entity(name=...)` overrides (`entity_table_map` is keyed by Java class name only, so an override query correctly reports "not found" rather than a wrong resolution); simple-name collisions across packages (map entry is `status: "contested"`; lineage refuses — see the contested-sentinel note below); polymorphic `FROM` (naming a superclass/interface — inherently multi-table under JOINED/TABLE_PER_CLASS inheritance); embedded/composite keys (`@EmbeddedId`/`@IdClass` paths like `i.id.customerId`, which need embeddable-aware resolution a flat class-name map doesn't provide). See `resolve_jpql_to_lineage()`'s own docstring for the authoritative, most up-to-date version of this list.

4. **No published precedent for `spring_drift_check.py`'s specific drift-detection design** (tier-1 whole-repo file-hash, tier-2 targeted per-citation ast-grep re-verification) was found in a 2026-07-23 arXiv search. ## Confidentiality/handling rules

1. **Standing rule** (promoted here from one-time handoff prose per `claude/steering-prompts/03-constraints-research-prompt.md`, which named it "the real-repo-name/content rule" but whose exact original wording isn't reachable from this repo — this is a fresh statement of the same intent, not a verbatim carry-forward, and should be treated as a first draft to reconcile against the original if that text ever resurfaces): **when this plugin is run against a real target repository, that repository's actual name and any excerpt of its actual source, config, or generated docs must not be pasted into this plugin's own tracked files** (commit messages, `claude/session-log.md`, steering-prompt research, issues) beyond what's needed to describe a bug mechanically (e.g., "a `vendor/` directory containing Java" is fine; a real client's package names or entity names are not). Use synthetic or already-public example names instead, the same way this repo's own `scripts/test_fixtures/spring_signals/` fixture tree does.

   **[Violated and fixed, 2026-07-25 — the rule needed widening, not just obeying]** This rule was broken by the very mechanism written to enforce it. `.gitignore` carried `/<real service name>/` so that a stray `git add -A` could not publish a ~101MB third-party checkout — but `.gitignore` is itself tracked, and this repo is public, so the ignore rule published the one thing it existed to protect: the directory name alone identifies the client service. The list above ("commit messages, `claude/session-log.md`, steering-prompt research, issues") enumerates *prose* carriers and simply did not imagine a config file leaking a name. **Read it as covering every tracked file, including ones nobody thinks of as documentation** — `.gitignore`, workflow YAML, fixture paths, `Makefile` targets. Fixed by moving the machine-specific name into `.git/info/exclude` (per-clone, never pushed) and leaving only generic patterns plus a pointer in `.gitignore`; the exposure never reached `main`. Caught by the repo owner on review, not by any check — the only mechanical gate that looks for this is `check_no_client_identifiers.py`, and it covers only the aggregate-JSON carrier from bytecode-oracle runs, not the `.gitignore` case, which is why the rule remains defended primarily by convention.
2. **[Resolved, heuristically — not a guarantee] Secret/credential leakage into generated docs**, found during a 2026-07-23 audit. The deterministic layer stays exactly as clean as before: `spring_signal_scan.py` still never reads config *values* into its own output — but it now also runs a heuristic pass (`src/doc_engine/scanning/support/_secret_heuristics.py`: secret-shaped key names with a non-placeholder literal value, plus key-agnostic patterns for AWS access key IDs and PEM private-key blocks) over configuration/deployment files and records `redaction_zones` (file + line + which heuristic fired, never the matched value) in `spring_signals.json`. `agents/file-summarizer.md` and `agents/doc-writer.md` are both instructed to never transcribe a flagged line's literal value, and `doc-taxonomy.md`'s configuration.md notes now say so explicitly (previously only warned against *fabricating* example secrets, said nothing about echoing a real one). Defense in depth, not just a prompt instruction: `src/doc_engine/tools/check_no_secrets_leaked.py` re-applies the same heuristics to a completed run's own output (`summaries.json`, `docs/*.md`) and flags anything that made it through anyway — documented in `SKILL.md` as an optional post-run check, not CI-wired (no target-repo output exists in this repo's own CI to check). Stated residual scope: heuristic, not exhaustive — a secret under an unrecognized key name, embedded in free-text prose rather than a reproduced `key: value` line, isn't caught unless it also matches one of the two key-agnostic patterns. See `_secret_heuristics.py`'s own docstring for the exact boundary.

   **[New info — the stated scope held in principle but not on line 1, fixed 2026-07-24]** This entry claimed the heuristic pass runs over configuration/deployment files, and it did — except on the first line of any BOM-prefixed file. `spring_signal_scan.py` read config with `encoding="utf-8"` rather than `utf-8-sig`, so a BOM survived as a literal `﻿`, which is Unicode category `Cf` and therefore matches neither `\s` nor `\w`. Every `^\s*`-anchored regex downstream (`_config_keys.py`'s `_YAML_KEY_LINE_RE`, `_secret_heuristics.py`'s `KEY_VALUE_LINE_RE`) failed on that line: a credential sitting on line 1 of a BOM'd `application.yml` was never flagged, and when line 1 was a group header it never entered the indent stack, so every descendant key silently lost its prefix (`spring.datasource.url` became `datasource.url`). Now reads `utf-8-sig`; regression-tested against byte-identical BOM/no-BOM twins in `scripts/test_enterprise_kitchen_sink.py` (`Ch04EncodingTest`). Noted rather than silently corrected because the failure was invisible from the output — the key set looked plausible and was wrong.

**A second, complementary signal for repos where config files are checked-in placeholders, not real secrets** (real values injected by an external service at deploy time — value-content heuristics matter less there, since nothing sensitive is actually committed): `spring_signal_scan.py` also records each config/deployment file's dotted key *set* (`config_key_sets`, names only, schema_version >= 5, `_config_keys.py`), and `spring_drift_check.py` uses it to tell apart two very different reasons a config file's content might change between scans — a key added/removed (`config_structure_changed`, an expected, structural evolution) versus the exact same keys with different values (`config_values_only_changed_review_needed`, worth a human look since nothing should be editing a value in-repo if the key structure didn't need to change too). See `spring_drift_check.py`'s "WHAT HAPPENS TO CITATIONS WITH NO rule_id" docstring section for the full design.

3. **New rule, partially mechanically enforced — external research must not carry the target repo's own real identifiers outbound.** `software-architect-and-testing`'s `WebFetch`-based external research (arXiv, GitHub, deepwiki.com — see its "External research" section) can construct a query or fetch built from real class/package/table/business-domain names it read via `Read`/`ast-grep`/`semgrep`, sending them to a third party as part of formulating what to search for. Items 1 and 2 above cover data flowing into this plugin's own tracked files, and into its generated docs, respectively — neither covers data flowing *outbound* over the network to a party outside either boundary. The rule: external queries/fetches must be framed around the general technology/pattern/library/concept (e.g. "Spring Kafka idempotent consumer pattern"), never the target repo's own real identifiers — not a class name, table name, business term, or anything recorded in `redaction_zones`. 
   
   **Enforcement:** (1) Instruction-based in `agents/software-architect-and-testing.md`'s "External research" section — the same honest hedging item 2 above uses for secret redaction ("not a guarantee"): nothing mechanically re-checks a query string against the repo's own identifier list before it goes out. (2) Gateway-based as of 2026-07-26: `software-architect-and-testing` declares `Bash` tool access, and every agent granted `Bash` now has `curl`/`wget`/`git clone` denied outright by `hooks/deny_raw_network.py` (runtime half) and check F in `check_repo_claims.py` (static half), the same two-tier policy `hooks/deny_text_search.py` enforces for the Grep tool — cross-linked at Integration-gaps item 2 below. This gates the mechanism (raw shell network calls bypass `WebFetch`'s citation discipline) rather than the content (whether a query contains an identifier), which is the structural half of the defense. The content half (instruction-based, reused) remains only as strong as `software-architect-and-testing`'s own prompt discipline.
