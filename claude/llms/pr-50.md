## Summary

One commit. It answers a question rather than shipping a feature: **should a Rust/tree-sitter fingerprint go into `spring_drift_check`, whose subjects really are Java files?**

That was the one place the previously withdrawn `astsig` proposal might have had an honest home — the earlier withdrawal turned on `_ast_signature.py`'s subjects being 0-of-22 `.java`, which is a fact about *that* module, not about the drift checker.

**Measured answer: the ceiling on what any better fingerprint could buy is 2 wrong verdicts in 208, and a ~30-line stdlib tokenizer already reaches it.**

| identity relation | false positives | missed real changes |
|---|---|---|
| `first_line` — status quo | **2 / 208** | 0 / 2 |
| `collapse_ws` | 2 / 208 | 0 / 2 |
| `strip_ws_outside_strings` | **0 / 208** | 0 / 2 |
| `tokens` | **0 / 208** | 0 / 2 |

Per perturbation against the status quo: `add_comment` 0, `reindent` 0, `blank_lines` 0, `wrap_annotation_args` **2** — all in `api_surface__mapping`. One specific class of edit, not general brittleness.

## The cause is not a missing parser, which is why no parser fixes it

ast-grep already returns the **whole** match. `spring_signal_scan._first_line_match()` keeps `text.splitlines()[0]`:

```
ast-grep returns : '@RequestMapping(\r\n        "/api/invoices"\r\n)'
stored identity  : '@RequestMapping('        <- compares equal to nothing
```

That function supplies the citation identity for **20 of 23** ast-grep rules — `persistence__entity`, `persistence__repository` and `raw_queries__query` are the three exceptions and re-derive structured identities instead. The structural information is in hand and being discarded on the Python side, so a tokenizer and a tree-sitter parse start from the same string and the string is already correct.

## The instrument was wrong first — the part a reviewer should weigh most

The first run reported **7/208 across five rules**. Artifact: the perturbation rewrote annotation-looking text *inside comments*, broke a doc comment's closing quote, and left the files unparseable — ast-grep then returned nothing and every citation in them read as drift.

A **3.5x overstatement, in the direction that would have justified the work under evaluation**, caught only by opening the files by hand.

Two structural consequences, both shipped:

- A **validity gate**: a formatting-only edit must leave the same citation count discoverable by a fresh scan. An edit failing it is not scored at all, rather than scored leniently.
- The broken perturbation is **kept as a test input** (`java_perturbations.broken_wrap_annotation_args`), with `Test00HarnessValidityGate` asserting the gate rejects it, and a third test asserting it *would* have produced drift verdicts — so the gate is demonstrably load-bearing rather than decorative.

## Two arms, because one is trivially winnable

An identity function returning `""` scores a perfect zero on false positives and detects nothing. Every row above is paired against a semantic-change corpus (a mapping path, an HTTP verb, an `@Table` name), and `test_no_candidate_buys_that_by_missing_a_real_change` asserts no candidate bought its zero that way.

The expected-drift set is **hand-labelled**, not derived from a fresh scan — deriving it would grade the checker against a restatement of its own comparison.

`collapse_ws` is present as a **recorded negative result**: the obvious first fix, which does not work, since `@Get( "/x" )` still differs from `@Get("/x")`. Pinned so it is not re-proposed.

`tokens` is preferred over `strip_ws_outside_strings` at equal measured cost because it is injective and the other is not — `strip_ws_outside_strings("int a") == strip_ws_outside_strings("inta")`. Asserted rather than asserted-about.

## What is deliberately not here

**The fix.** `_first_line_match()` does two jobs: it decides what tier 2 *compares*, and what `spring_signals.json` *stores* as each citation's `match` field — human-readable evidence a `doc-writer` agent consumes. A token sequence joined by `\x1f` is a fine identity and unreadable evidence. Separating the two changes the stored schema, so it is its own decision with its own blast radius.

Recorded as `CONSTRAINTS.md` "Known precision tradeoffs" item 9, flagged not resolved. The fixtures already contain one instance of the defect in committed data: `InvoiceController.java`'s multi-line `@PreAuthorize` is stored as the truncated `@PreAuthorize(`.

## The Rust question, answered

**No, for the fingerprint.** Ceiling 2/208; Python stdlib already reaches it. Adding a compiled binary to collect a gain already collected would put a required toolchain in front of a plugin shipping as a git checkout with 0 releases and 0 tags.

**One real case remains, in the test lane rather than the shipped path.** The validity gate is a *proxy* — count unchanged — which caught the real defect but could pass while a file stays broken in a way that does not move a count. A direct oracle would assert AST equivalence modulo whitespace and comments, needing a Java parser:

- Python stdlib has none.
- **ast-grep cannot stand in, verified on 0.44.1.** `--strictness relaxed` is exactly the right relation ("ast nodes except comments"), but a whole file cannot be a pattern — `Error: Multiple AST nodes are detected`. `--debug-query` dumps the *query*'s tree only. No tree-dump subcommand; `ast-grep outline` yields one line for a 26-line annotated Java fixture.

Test-lane only, so `00`'s "Python stdlib, `ast-grep` on PATH, no new services" runtime constraint stands unamended. **Stated in the research doc, not acted on** — it should carry its own measurement first, the same discipline that killed the first Rust proposal and reversed the `t1` default before it.
