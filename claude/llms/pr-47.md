# PR #47 — Kitchen-sink suite, a code-quality ratchet, and five real bugs

## Summary

Seven commits. Two (`021c83e`, `b568d7f`) predated this session; five landed with it.

1. **`a482c0d` — kitchen-sink end-to-end suite, and the three bugs writing it found.** Every prior suite tested one script in isolation, in-process. Nothing ran the documented command series as real subprocesses, and no fault injection ever closed the loop to a process exit code — so **every gate in this pipeline was proven only to populate an issues list, never to actually fail a run.** The three bugs were found by building a hostile fixture, not by reading code: `build_groups()` could loop forever (a hang, not a wrong answer — Stage 0 never returns); ast-grep's stdout was decoded with the locale codec, crashing on some UTF-8 and silently mojibake-ing the rest into cited documentation; config files were read as `utf-8` rather than `utf-8-sig`, so a BOM broke every `^\s*`-anchored regex on line 1.

2. **`90f5ff6` — the code-quality ratchet.** `ruff` took `scripts/` from 617 findings to zero. `check_code_quality.py` added a committed per-function baseline that fails on *regression only*. Two design notes, both learned by the gate firing on its own author: it measures **statements, not line span** (the first draft flagged a function that had grown only by an explanatory comment, in a repo that is deliberately 38–54% prose), and annotation coverage counts **production modules only** (otherwise adding a test suite lowers the ratio and fails the build).

3. **`43eea32` — two live defects the measurement pass surfaced.** `capacity_preflight.py` emitted OS-native paths into a join expecting forward slashes — the *third* occurrence of a bug `partition_repo.py` documents being fixed twice already. And `run_ast_grep()` still called `sys.exit(1)` from library code, the exact thing `AstGrepNotFoundError` was introduced in that same file to stop; the original fix converted `find_ast_grep()` only.

4. **`744f1de` — stop naming a client service in `.gitignore`.** The ignore rule existed so a stray `git add -A` could not publish a third-party checkout, but `.gitignore` is tracked and this repo is public, so the rule published the one thing it existed to protect. The machine-specific name moved to `.git/info/exclude`; `CONSTRAINTS.md`'s confidentiality rule was widened from a list of *prose* carriers to every tracked file.

5. **`106b0eb`** — a `tool-quirks.md` entry, authored by a concurrent session.

## What a reader should know that the diff does not show

**This branch's history was rewritten and force-pushed.** The client service name was introduced in the pre-session commit `b2410fd` and therefore sat in the branch's *history*, not just its tip — a normal merge would have carried it into `main`'s history permanently. All seven commits were rewritten so no commit contains it, verified across the range, then force-pushed with `--force-with-lease`. **`main` never contained the name.** The SHAs above are post-rewrite; pre-rewrite SHAs no longer resolve.

Two commits in this PR (`90f5ff6`, `106b0eb`) were authored by a **concurrent session** working in the same tree, not by the session that opened the PR.

10. **Claim (the important one): no commit reachable from `main` contains the redacted directory name.** This is the check that the history rewrite actually worked, and the one worth running rather than trusting.

    **The name is deliberately not written in this file.** Writing it here as a grep pattern would republish, in a tracked public file, precisely what the rewrite removed — the same mistake in a new location. It lives in your local `.git/info/exclude`, which is per-clone and never pushed, so the check reads it from there:

    ```bash
    NAME=$(grep -oE '^/[^/]+/$' .git/info/exclude | tr -d '/' | head -1)
    test -n "$NAME" || echo "no local exclude entry — nothing to check against"
    git rev-list 1539d0c | while read -r c; do
        git show "$c" | grep -q "$NAME" && echo "LEAK in $c"
    done
    ```

    Expect: no output. A fresh clone has no `.git/info/exclude` entry, so this check reports that it cannot run rather than passing vacuously — which is the intended behaviour, not a gap.
