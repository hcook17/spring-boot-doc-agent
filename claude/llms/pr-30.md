# PR #30 — Fix two JPQL-provenance gate misses in `spring_drift_check.py`

## Summary

PR #28 added `_reverify_jpql_lineage_provenance()`, which named the right invariant — *a citation is fresh iff every file in its provenance is unchanged* — but its gate did not fully enforce it. Two cases slipped through, and both produced a **confidently wrong** verdict rather than a loud failure, which is precisely the class the pass exists to prevent.

1. **`STATUS_CONFIRMED` false negative.** The gate skipped any citation whose own-file verdict was not `STATUS_UNCHANGED`. But `_recheck_queries()` returns `STATUS_CONFIRMED` when the query's file changed and its query *text* is intact — and text presence says nothing about whether the derived lineage is still accurate. So renaming an entity's `@Table` *and* making any unrelated edit in the repository file reported `confirmed_still_present` over stale lineage.
2. **Deleted entity file.** The gate keyed on `changed_set` only, while `classify_files()` reports a delete — and a move, as a delete of the old path — in `deleted`. Deleting an entity's file left the dependent JPQL citation sitting at tier-1 `STATUS_UNCHANGED`.

The fix widens the guard to `(STATUS_UNCHANGED, STATUS_CONFIRMED)` and threads `deleted_set` through, with a delete-specific detail string. The statuses still deliberately left alone (`STATUS_DRIFTED`, `STATUS_FILE_DELETED`, the `*_NO_SIGNATURE` family) now carry an inline comment saying why each is skipped, rather than being covered by a single blanket condition. No new status constant.

Also corrects three stale docstring references found alongside the bug:

- `spring_signal_scan.py` and `test_spring_signal_scan.py` pointed readers at `_query_citations_depending_on_entity()` and `_flag_stale_jpql_lineage()`. **Neither has existed at any commit** — they read like names from a design draft that were renamed before implementation landed. The real names are `_raw_query_entries_with_resolved_entity()` and `_reverify_jpql_lineage_provenance()`.
- Two comments dated bounded JPQL resolution to `schema_version 3` and called it "the same release as native-query lineage." It shipped under `schema_version 5`; native-query lineage was 3. The same file already said `6` for `resolved_via_entity`, so it contradicted itself.

Tests: 36 → 41 in `test_spring_drift_check.py`. Full suite 236 passing, 6 intentional skips.
