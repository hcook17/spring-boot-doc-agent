# Research + scaffold prompt: categorizing and indexing claude/tool-quirks.md for efficient routing and retrieval

Self-contained — read this without assuming any other conversation's context. First read `claude/steering-prompts/00-shared-research-standards.md` for the research bar and methodology every finding here must meet.

## The gap

`claude/tool-quirks.md` (see `skills/tool-quirks/SKILL.md` for the full convention) is a 2026-07-24 addition: an append-only index of odd behavior in the *ambient tools/environment* this repo is worked in (`gh`, `git`, GitHub's own API/UI, Windows/Git-Bash quirks) — distinct from `claude/session-log.md` (steering-prompt impact) and `claude/llms/` (this repo's own PR-verification commands). As of this prompt being written it already has four entries spanning genuinely different categories with no shared structure beyond a common prose template: a `gh pr create` title/body mismatch (a `gh`-CLI quirk), a Cowork session's GitHub web-UI review getting stuck on JS-rendered diffs (a browser/API-fetch quirk), a `gh api repos/.../pulls/<N>` endpoint returning a stale `.head.sha` for 30+ seconds after a fast push (an API-caching quirk), and pushing commits to a PR branch after it had already merged, which silently strands them off `main` (a process/workflow gap, arguably not a "tool quirk" in the same sense as the other three at all).

`skills/tool-quirks/SKILL.md`'s current instruction for checking this file before investigating something new is just "search `claude/tool-quirks.md` for an entry matching the symptom or the tool/command involved" — i.e., full-text search of a single growing markdown file, with no tags, no index, and no category boundaries. That works fine at four entries. It will not obviously keep working at forty: a future session with a narrow, tool-specific symptom (e.g., "is this a known `gh` quirk?") has no fast way to filter to just the `gh`-related entries, no way to distinguish "pure tool bug" entries from "process gap, not really a tool's fault" entries (the fourth entry above is a live example of a categorization edge case worth resolving explicitly, not silently), and no stated threshold for when a single flat file should split into something else (per-category files, a structured index alongside the prose, etc.).

This repo already has one relevant precedent worth checking before designing anything new: `claude/llms/README.md` indexes `claude/llms/pr-N.md` via a simple table (PR number, title, state) — but that index has a natural single-dimension sort key (PR number) that `tool-quirks.md` entries don't share (they vary along multiple axes: which tool, what kind of symptom, resolved vs. unresolved). Don't assume that table pattern transfers directly; verify whether it does or whether tool-quirks entries need genuine multi-tag categorization instead.

## Research

Search GitHub and arXiv for how existing incident-management/runbook/postmortem tooling categorizes entries for fast retrieval (tagging taxonomies used by tools like PagerDuty/Blameless-style postmortem indexes, or any open-source "known issues" / "gotchas" doc convention in a popular CLI tool or SDK repo) — apply the shared standards' star/push/DeepWiki methodology to any GitHub repo candidate.

Separately, check whether Anthropic's own skill-discovery mechanism is a relevant model here: Claude Code skills are routed to by natural-language description matching (a skill's frontmatter `description` field), not by an explicit tag taxonomy — `anthropics/skills`' `skill-creator` and this plugin's own `SKILL.md` files already rely on that. Investigate whether the same "richly-described, matched by an LLM reading it" approach is actually sufficient for `tool-quirks.md` retrieval (i.e., maybe no structured tagging is needed at all — a future session reading the whole file and matching by understanding, not by grep, might already be "efficient enough" given the file's expected size), versus whether a genuine keyword/tag index is needed because a session might reasonably want to check this file *before* investing in full comprehension of every entry (the stated purpose in `skills/tool-quirks/SKILL.md`: "check before deep-diving," implying a cheap pre-check, not a full read).

Check for a lightweight, no-new-dependency way to do structured search over markdown files (grep against a consistent per-entry `Tags:` line, versus a separate structured index file, versus frontmatter per entry) that fits this project's existing stdlib-only, no-new-infrastructure ethos (`00-shared-research-standards.md`'s "what scaffold and implement means") — don't reach for a vector-search/embeddings dependency without first confirming plain keyword tagging is actually insufficient at the scale this file is likely to reach.

## What to scaffold and implement

1. Decide on (and state explicitly, don't leave implicit) a fixed, small tagging vocabulary for the *kind* of entry (e.g., `gh-cli`, `github-api`, `git`, `shell/windows`, `mcp-tool`, `process-gap` — confirm or revise this list against what the four existing entries and any new ones actually need, don't invent categories nobody has hit yet) and retrofit the existing four entries with it — small enough right now to do by hand rather than needing a migration script.
2. Add a compact index (a table, likely at the top of `claude/tool-quirks.md` itself unless research in step above suggests a separate file is cleaner) with, at minimum: date, one-line symptom, tag(s), status. Modeled on but not copy-pasted from `claude/llms/README.md`'s table — confirm whether a single-key sort still makes sense once tags are multi-valued, or whether the index needs to be groupable/filterable by tag instead of just chronological.
3. Update `skills/tool-quirks/SKILL.md`'s "Before deep-diving" section to point at the new index/tags first, not a full-text search of the whole file, and resolve the categorization edge case named above explicitly (is "pushed after a PR merged" a tool quirk, a process gap, or does this file need a second, sibling file for process gaps that aren't really about a tool misbehaving at all — decide and state the reasoning, don't leave it ambiguous).
4. State an explicit threshold (entry count or file size) at which a single flat file should be reconsidered (split by category, or converted to frontmatter-per-entry with a generated index) — this project's own convention elsewhere (`capacity-preflight`'s fan-out thresholds, `partition_repo.py`'s token budget) is to name a concrete, tunable number rather than leave "when this gets too big" as a vague someday. Pick one, mark it as a heuristic guess pending real experience, the same posture those other thresholds use.
