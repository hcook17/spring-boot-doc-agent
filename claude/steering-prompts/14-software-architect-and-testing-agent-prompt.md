# Task prompt: add a software-architect-and-testing review agent to the pipeline

Self-contained — read this without assuming any other conversation's context.

Context: `spring-boot-doc-agent` (this repo) documents a *target* Spring Boot repository through five pipeline stages (`skills/document-spring-repo/SKILL.md`), each stage backed by one of five `agents/*.md` subagents. None of the five reviewed the target repo's architecture or test suite against an explicit body of theory — `architect-segment`/`architect-merge` describe *what* the architecture is, but nothing assessed it against, say, DDIA's partitioning/consistency tradeoffs, and nothing assessed the target repo's test suite against a testing-design framework at all. `claude/steering-prompts/10-review-persona-and-standards.md` §5-6 already anchors DDIA 2e and testing/security literature (Meszaros, Ross Anderson, OWASP LLM Top 10) — but exclusively as a lens for reviewing *this plugin's own* fact-store design, one layer up from what a pipeline run actually produces for a user.

Separately: no agent in this pipeline had `WebFetch`/`WebSearch` (confirmed by reading all five `agents/*.md` frontmatters), so nothing could ground a claim about an external library or comparator repo in live research — despite `claude/steering-prompts/00-shared-research-standards.md` already defining exactly that methodology (arXiv, GitHub filtered by stars/recency, DeepWiki-as-orientation) for steering-prompt authors. And `semgrep` existed in this repo only as a one-off oracle-comparison script (`scripts/stage0_oracle_compare.py`) and an uncommitted local exploration (`.claude/settings.local.json`) — never as a wired, pinned dependency or a first-class agent tool, despite the ast-grep mandate (`CLAUDE.md`) never having ruled it out; ast-grep and semgrep solve different matching problems (single-pattern tree-sitter matches versus "presence of A without presence of B in the same scope," which is semgrep's own idiom).

This task closed all three gaps at once with one new agent, `software-architect-and-testing`, reviewing the *target* repo (not this plugin) through DDIA 2e and *Effective Software Testing* (Aniche, Manning — a distinct book from Meszaros's *xUnit Test Patterns*, which prompt 10 §6 already anchors for a different purpose), grounding external-fitness claims in the existing arXiv/GitHub/DeepWiki methodology, and using `ast-grep` plus a newly-curated `semgrep` ruleset.

## What landed

1. **`agents/software-architect-and-testing.md`** — sixth pipeline agent, `tools: Read, Glob, Write, Bash, WebFetch` (no `Grep`). Reviews the target repo through the DDIA/testing lenses; reaches for bounded external research (DFS `MAX_DEPTH=5` / BFS `MAX_RINGS=3,RING_WIDTH=7` per `claude/steering-prompts/11-context-traversal-protocol.md`) only when a finding genuinely hinges on external fitness, tagging every source's evidence tier (A/B/C) and never treating Tier C (deepwiki.com) as sufficient on its own.
2. **`scripts/spring_semgrep_rules.yml`** (10 rules: 5 `architecture_ddia__*`, 5 `testing_est__*`) + **`scripts/semgrep_rule_fixtures/`** (one fixture per bucket) + **`scripts/semgrep_rule_coverage.py`** (non-vacuity + backtest/ratchet, mirroring `rule_coverage.py`'s split exactly) + **`scripts/test_semgrep_rule_coverage.py`**. Verified directly against a real `semgrep` binary: 10/10 rules fire, 13 total findings on the fixture corpus.
3. **`semgrep~=1.171.0`** pinned in `requirements.txt`; `.github/workflows/ci.yml` gained a version-pin-verification step (mirroring the existing `ast-grep` one), a `semgrep_rule_coverage.py` non-vacuity step, and a `test_semgrep_rule_coverage.py` step. `.claude/settings.json` gained `Bash(semgrep scan:*)`/`Bash(semgrep --version)` allow entries.
4. **Pipeline wiring**: `skills/document-spring-repo/SKILL.md` Stage 3 now dispatches `software-architect-and-testing` in the same turn as `gap-analyzer` (a new `architecture_testing_review` manifest stage, tracked separately from `gap_analysis_interview` since only the latter includes the live interview). Its output (`architecture_testing_review.json`) becomes a fifth input, `arch_test_review`, feeding only the `architecture.md` and `testing.md` `doc-writer` dispatches (`doc-taxonomy.md`, `agents/doc-writer.md`).
5. **Citation-grammar scope decision, deliberate**: the closed, mechanically-enforced four-word tag grammar (`doc_tag_utils.py`'s `TAG_WORD_SPAN`) was **not** extended with a fifth word for external research. `[Evidenced]` stays reserved for a fact readable at a cited location in the target repo; the DDIA/EST concept name and any external-research trail are attributed **prose**, the same way `claude/steering-prompts/10-review-persona-and-standards.md` §5-6 already cites DDIA/Meszaros/arXiv — not a new bracket tag. Extending the tag grammar would have rippled through `doc_tag_utils.py`, `run_manifest.py`'s tag counting, `test_pipeline_stages.py`'s grammar assertions, and `citation_coverage.py`'s heuristics — a materially larger, separate-decision change this task didn't take.
6. **Mechanical pipeline-tracking updates**: `scripts/capacity_preflight.py` (`STAGE3_ARCH_TEST_REVIEW_FANOUT`, formula now `2*num_groups + 17`), `scripts/run_manifest.py` (`PREFLIGHT_TO_MANIFEST_STAGE` gained `stage3_software_architect_and_testing → architecture_testing_review`, tracked as its own manifest stage rather than folded into `gap_analysis_interview`), `scripts/test_pipeline_stages.py` (`ArchitectureTestingReviewShapeTest` + `validate_architecture_testing_review_findings()`, including a regression test for the Tier-C-alone case). `scripts/check_repo_claims.py` gained `derive_semgrep_rule_count` alongside the existing `derive_ast_grep_rule_count`.

## What NOT to do here (learned while doing this)

- Don't invent a new bracket-tag word for external research — see point 5 above. If a future session wants formal per-source citation tagging for DDIA/EST findings, that is a real, separate, larger task (touches four files' grammar enforcement), not a small addition to this one.
- Don't fold `software-architect-and-testing`'s manifest stage into `gap_analysis_interview` just because they're dispatched in the same turn — they're tracked separately because one includes the live interview and the other doesn't, and `run_manifest.py`'s tie-in needs to be able to attribute a predicted/actual mismatch to whichever of the two actually drifted.
- Don't add `semgrep` to the deterministic Stage 0 signal-scan layer (`spring_signal_scan.py`) — that layer stays ast-grep-only by design; `semgrep` is scoped to this one agent's own ruleset.
- Don't fabricate a real-repo semgrep backtest baseline (`scripts/semgrep_rule_coverage_baseline.json`) — none exists yet, honestly, the same way several other backtest-only measurements in this repo are stated as "not yet run against a real repo" rather than invented.
